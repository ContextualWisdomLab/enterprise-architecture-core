# Product / Technical Gap Baseline

This is the executable correction ledger for the Enterprise Architecture Decision Plane. It distinguishes shipped/default-branch truth, unmerged stack evidence, accepted architecture and external governance. A documented gap stays open until source/tests/settings prove the correction; wording alone does not close it.

## State model

- **Shipped/default-branch truth**: behavior present on the current repository default branch.
- **Active PR**: implemented only on an unmerged exact head; not shipped.
- **Accepted architecture**: responsibility/invariant that new work must obey.
- **Open DDD debt**: verified ownership/path/module debt requiring a mapped structural correction.
- **External governance**: an administrative/trusted-tool boundary owned outside this repository; this repository fails closed until it changes.
- **`planned_ui`**: an accepted presentation surface with no executable current-head UI evidence. Documentation diagrams or inventory prose do not make it shipped.

## Structural correction sequence

The historical package is not renamed as cosmetic churn. Before moving a bounded slice, enumerate public imports, internal dependencies, OpenAPI/AsyncAPI/schema paths, database migrations, tests, workflow/package metadata and external consumers. Add a regression for the intended dependency direction, move one coherent responsibility, provide a versioned adapter only when an actual consumer requires it, and remove the old path after the deprecation window. A modular monolith remains the default while these contexts share transaction/deployment cohesion.

The first bounded correction moved the broad process/HTTP implementation out of the generic `service.py` path without changing its behavior or breaking its import surface. That compatibility step is intentionally incomplete: new behavior must target `decision_plane_http.py` or a more specific bounded-context path, while internal consumers and the broad implementation are decomposed in subsequent mapped slices.

The connector-catalog correction applies the same rule to the Cross-Domain Evidence Projection Supporting context. The executable validator lives in `cross_domain_evidence/connector_catalog.py`; `validation_connector_catalog.py` only re-exports the existing public names. A focused architecture regression fails if the owner path disappears, behavior returns to the facade, or the compatibility import stops resolving to the exact owner functions and exception/report types. This is one mapped move inside the existing package compatibility window, not a claim that the whole foundation-era package is decomposed.

The reassessment-status validator validates a foreign Data/AI Context evidence projection/read surface and therefore belongs to the Supporting context rather than the historical technical validation bucket. `cross_domain_evidence/data_management_recheck_status.py` owns that contract-validation behavior; `validation_data_management_recheck_status.py` is compatibility-only, and the fitness test requires exact public-object aliasing so existing imports do not silently fork validation semantics.

The adjacent EA-owned decision behavior is deliberately not placed in that Supporting context. `portfolio_assessment/data_management_recheck.py` owns the reassessment command, `portfolio_assessment/data_management_recheck_status.py` owns the follow-up status read, and `portfolio_assessment/portfolio_assessment.py` owns portfolio assessment read/summary behavior. Their historical root modules re-export the same public objects without executable domain behavior. The terminal replan runtime now consumes these owner paths directly. This separates foreign evidence admission from EA-owned assessment decisions while preserving the current import contract.

Transformation execution follows the same owner-first rule. `strategy_transformation/start.py` owns the purpose-bound start request, authorization profile and PostgreSQL command port; `strategy_transformation/complete.py` owns the corresponding completion boundary. Historical root `start.py` and `complete.py` only re-export the public objects. The move preserves the stored-command, idempotent receipt and transactional-outbox contracts; it does not make HTTP composition or the Generic authorization adapter a new source of transformation truth.

Target-state verification and governed replanning are adjacent Strategy & Transformation commands. `strategy_transformation/verify.py` owns the evidence-backed verification request, authorization profile and stored-command adapter; `strategy_transformation/replan.py` owns the replacement-plan request and immutable replan evidence command. Historical root `verify.py` and `replan.py` are behavior-free compatibility facades with exact public-object identity. `verification_runtime.py` and `replan_runtime.py` compose those canonical owners directly. Verification preserves the `verified` versus `gap_detected` transition decision; replanning creates a distinct replacement transformation without rewriting the terminal predecessor.

Target-state monitoring is the adjacent Strategy & Transformation read side. `strategy_transformation/monitor.py` owns the purpose-bound monitoring request, monitoring authorization profile and tenant-bound PostgreSQL query port; historical root `monitor.py` only re-exports the same public objects. `completion_runtime.py`, `verification_runtime.py`, `monitoring_runtime.py` and `replan_runtime.py` compose the mapped start/completion/verification/replanning/monitoring owners directly rather than depending on their compatibility facades. The move preserves the freshness-state calculation, valid/business versus recorded/system time checks, UUIDv7 identity validation and stored-function boundary. These Strategy & Transformation corrections remain unproven until their exact current head receives executable repository evidence.

Identity and authorization is a coherent Generic adapter rather than another root technical bucket. `identity_authorization/authorization.py` owns Keyverse/OIDC/JWT verification and verified tenant/role/subject binding; root `authorization.py` resolves to that same module object for compatibility. Moved Portfolio/Strategy ports and the completion/verification/monitoring/replan runtime extensions now consume the canonical adapter directly, and those runtime extensions use `decision_plane_http.py` instead of the historical `service.py` facade where mapped. This is consumer migration, not authority transfer. Other broad root consumers remain explicit debt until their responsibilities are proven and their exact-head tests execute.

The Quarantine Sandbox Runtime slice deliberately records only a connector/ACL boundary. It does not copy Rust runtime types, Podman/container mechanics, malware verdicts, artifact risk scores, runtime storage or caller policy into EA. The connector can advance from provisional to integrable only when both the runtime and Context Graph dependency have immutable released identities that the EA release gate can verify.

The architecture-fitness tests block new generic buckets, direct foreign implementation imports, renewed behavior in the moved compatibility facades and runtime reintroduction of already-moved root facades, so the correction ledger cannot be used as permission to make the existing shape worse while a larger migration waits.

## Release statement

No active-stack capability, DDD correction, connector projection or buyer-facing planner flow is release truth until it is integrated on the intended protected `main` exact head and all applicable repository CI/security/coverage/migration/RLS/outbox-inbox/package/SBOM/provenance/reproducibility/review-policy/operational gates pass together. Every context-bound connector additionally depends on the immutable released `context-graph-contracts` identity recorded by `contracts/context-graph-dependency.json`. Quarantine integration additionally requires an immutable released Quarantine Sandbox Runtime consumer contract; neither its current Draft PRs nor CGC PR #21 are release evidence. This baseline is not evidence of certification, adoption, UI delivery or acquisition valuation.
